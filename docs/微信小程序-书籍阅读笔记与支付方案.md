# 慧灯阅读小程序：书籍下载 + 阅读 + 笔记 + 微信支付 可行性方案

> 对应 App：`3.4.1+33`（包名 `com.huideng.reader`），Flutter + 腾讯云开发（CloudBase）。
> 结论先行：**技术上完全可行，而且书籍/阅读/笔记是现有代码里最适合迁移的一块；
> 真正的门槛不在开发，在主体资质、内容类目和 iOS 虚拟支付规则。**
> 本文所有微信平台规则以官方最新文档/后台审核口径为准，落地前需再核一次。

---

## 0. 一页结论

| 问题 | 结论 | 说明 |
| --- | --- | --- |
| 书籍下载能做成小程序吗 | **能** | 正文是纯 `.txt`，8,982 本共 263MB（中位 27KB），改成“按需下载到小程序本地缓存”即可 |
| 阅读页面能还原吗 | **能，但要重写排版层** | Flutter 的 `TextPainter` 分页无法直接搬；建议先做“滚动 + 虚拟列表”，翻页二期 |
| 笔记能带过去吗 | **能，成本最低** | 现有 `api` 云函数已有 `getParagraphNotes` / `saveParagraphNote`，按 `sutraKey + 段落 index` 存储，小程序可原样调用 |
| 微信支付能接吗 | **能，但有硬条件** | 需企业/个体户主体 + 微信支付商户号；**iOS 端不能卖电子书/会员这类虚拟商品** |
| 最大风险 | 资质与审核 | 《互联网宗教信息服务许可证》、出版物经营资质、iOS 虚拟支付 |
| 建议路径 | 先免费版过审，再开支付 | 免费阅读 + 笔记先上线；支付只做 Android + 单本/会员，iOS 隐藏购买入口 |

**一句话：能做，但不要把它当成“把 App 的支付搬过去”——App 目前并没有付费内容，接微信支付等于新开一项收费业务，合规成本高于开发成本。**

## 1. 现有资产盘点（决定复用度）

| 模块 | 现状 | 小程序复用度 |
| --- | --- | --- |
| 正文文件 | `assets/sutras_ascii/**/*.txt`，8,982 本 / 263MB，中位 27KB，最大 594KB | ★★★★★ 纯文本，天然适合小程序 |
| 下载源 | GitHub raw + 3 个镜像（`sutra_downloader.dart`） | ★☆☆☆☆ 必须换源（GitHub 未备案，不能做小程序下载域名） |
| 书目 | `assets/sutras_catalog.json`（774KB，9k 条：标题/分类/字数/大小） | ★★★★☆ 放云端或 CDN，主包只留图标 |
| 分段规则 | `reading_page.dart` 的 `_parseParagraphs`：按行、`。。。` 隐藏操作栏、`///` 不分段、`@@` 备注块、`BBB` 加粗 | ★★★☆☆ 必须一比一移植成 TS，否则笔记对不上 |
| 阅读器 | 5,863 行，滚动 + 按段分页（`TextPainter`），字号/行距/背景/进度 | ★★☆☆☆ 交互可参考，排版层重写 |
| 段落笔记 | 云文档 `readingParagraphNotes`：`sutraKey`、`index`、`notes[]`、`underlines[]`、`done` | ★★★★★ 服务端与数据结构可直接复用 |
| 后端 | 单个 `api` 云函数（Node，约 240KB 单文件），CloudBase 环境 `randeng-d8gs968w22a3d98e8` | ★★★★☆ 小程序 `wx.cloud.callFunction` 可直接调 |
| 账号 | 手机号 + 短信验证码（CloudBase Auth） | ★★☆☆☆ 小程序改用 openid，需做账号绑定 |
| 支付 | **无**；`donate_page.dart` 只是个人收款码“资助” | ☆ 全新建设，且原“收款码资助”不适合搬进小程序 |

### 1.1 两个关键事实

1. **正文不是富文本，是“一行一段”的纯文本**，这大幅降低了迁移难度；
   真正的难点是“选文/画线”和“分页”，不是内容本身。
2. **App 目前没有付费书、没有订单、没有权益系统**。所以“接入微信支付”不是移植，
   而是新增：商品定价、订单、权益、退款、对账、客服，一整套都要新建。

## 2. 三条硬约束（先看这个，再谈功能）

### 2.1 主体、类目与资质

| 事项 | 要求 | 影响 |
| --- | --- | --- |
| 小程序主体 | 个人主体**不能**开通微信支付 | 必须企业 / 个体工商户（或政府、事业单位、社会组织） |
| 小程序认证 | 300 元/年 | 支付、手机号快速验证都以认证为前提 |
| 小程序备案 | 2023 年起新小程序须完成 ICP 备案后才能发布 | 增加 1–2 周 |
| 宗教内容 | 以宗教信息发布为主的平台，按《互联网宗教信息服务管理办法》可能需《互联网宗教信息服务许可证》 | **最大不确定性**；微信“宗教”类目审核会核验 |
| 付费电子书 | 图书销售通常要《出版物经营许可证》；网络出版服务要《网络出版服务许可证》 | 只有“收费”才触发；免费阅读可显著降低门槛 |
| 内容版权 |  CBETA 正文为公版，但标点/校勘整理版、讲记/开示类内容有版权 | 收费前必须厘清授权链 |

> 建议：**先用“免费阅读”版本去提审**，用审核结果验证类目，而不是先写支付。
> 如果连免费版都因宗教类目被拒，支付方案再完美也没有意义。

### 2.2 iOS 虚拟支付（决定商业模式）

- 微信小程序在 **iOS 端不支持用微信支付购买虚拟商品**（电子书、会员、内容解锁、课程等）。
  这是苹果规则 + 微信规范的叠加，不是技术问题。
- 可行的三种处理：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. iOS 不卖（推荐先做） | iOS 隐藏购买按钮，只展示免费书与已购内容 | iOS 用户无法付费；不能在小程序里引导去 App/H5 购买（违规） |
| B. 申请“小程序虚拟支付” | 用 `wx.requestVirtualPayment`，部分类目可在 iOS 合规收费 | 是否对“图书/阅读”开放、费率与分成以微信官方为准，需提前申请 |
| C. 卖实物 | 卖实体书/周边，走普通微信支付 | 与“只做书籍下载和阅读”的目标不符 |

- **绝对不要**在小程序里写“去 App 购买”“加微信转账”“复制链接到浏览器支付”，
  这类引导既违反微信规范，也会被苹果审核条款命中，基本必拒。

### 2.3 包体、缓存与“下载”的真实含义

| 限制 | 数值 | 应对 |
| --- | --- | --- |
| 主包 | 2MB | 只放代码、图标、骨架屏；书目与正文全部外置 |
| 总包 | 20MB（现行规则，若官方上调以最新为准） | 263MB 正文不可能打包 |
| 单分包 | 2MB | 按“书城/阅读/我的”拆包，阅读器独立分包 |
| 本地文件 | `wx.env.USER_DATA_PATH` 约 200MB | 足够缓存约 7,000 本中位书；需 LRU 清理 |
| 本地 Storage | 10MB | 只放进度、设置、书目索引，不放正文 |

> 小程序里的“下载”= **本地缓存**：用户看不到文件、不能导出到手机文件管理器、卸载小程序即清空。
> 如果产品要求“下载后能用第三方阅读器打开”，小程序做不到，这个需求要提前砍掉。

## 3. 推荐架构

```
┌──────────────────────────── 微信小程序（原生 TS） ────────────────────────────┐

└──────┬───────────────┬──────────────────┬──────────────┬──────────────────────┘
       │               │                  │              │
       │ 书目/搜索      │ 正文 fileID       │ 笔记 CRUD     │ 下单/查单
       ▼               ▼                  ▼              ▼
  api 云函数      CloudBase 云存储      api 云函数      pay 云函数
  （复用现有）     books/<卷>/<id>.txt   （复用现有）    （微信支付 v3 JSAPI）
       │               │                  │              │
       └───────────────┴──────────┬───────┴──────────────┘
                                  ▼
                    云数据库：sutras / readingParagraphNotes
                              orders / entitlements / users
```

### 3.1 为什么是“原生小程序”，不是 Taro / uni-app / Flutter

| 方案 | 判断 | 原因 |
| --- | --- | --- |
| 原生小程序 + TypeScript | **推荐** | 包体最小、审核最稳、阅读器性能可控、云开发调用最顺 |
| Taro / uni-app | 可选 | 若团队更熟 Vue/React，能省 UI 时间；但包体更大、长列表调优更绕 |
| Flutter 直接编译 | **不可行** | 官方不支持；mpflutter 等方案生态小、审核与稳定性风险高 |
| H5 + `web-view` 套壳 | **不建议做主方案** | 纯壳易被判“无实际小程序功能”；`web-view` 内不能调 `wx.requestPayment`；业务域名要备案；离线缓存不可控 |

> 阅读器若要更顺滑，可在二期评估 **Skyline 渲染引擎**；一期用 WebView 渲染 + 虚拟列表足够。

### 3.2 内容分发

1. 正文迁到 **CloudBase 云存储**：`books/<卷>/<id>.txt`，数据库存 `fileID`。
   - 云存储下载走 `wx.cloud.downloadFile`，**不占服务器域名白名单，也不需要域名备案**。
   - 这是绕开“GitHub raw 不能作为小程序下载域名”的最省事路径。
2. 书目从 `sutras_catalog.json` 导入云数据库 `sutras`（9k 条），或放 CDN 做 gzip JSON。
   - 列表分页 20 条/页；搜索走云函数（标题/拼音/编号），不要一次拉 9k 条。
   - 主包只保留分类图标和默认封面。
3. **付费书不要直接下发公开 fileID**：
   - 免费书：`fileID` 直接给客户端下载；
   - 付费书：`fileID` 不下发，云函数校验权益后用 `getTempFileURL`（有效期 5–10 分钟）
     或按“卷/章”返回文本；云存储权限设为“仅管理端可读写”。

### 3.3 下载器（对应 `sutra_downloader.dart`）

状态机：`未下载 → 下载中 → 已下载 → 可更新`。

```js
// 下载一本：云存储 fileID → 本地用户目录
const fs = wx.getFileSystemManager();

async function downloadBook(book) {
  const { tempFilePath } = await wx.cloud.downloadFile({ fileID: book.fileID });
  const dest = `${wx.env.USER_DATA_PATH}/books/${book.id}.txt`;
  await new Promise((resolve, reject) => {
    fs.saveFile({ tempFilePath, filePath: dest, success: resolve, fail: reject });
  });
  const text = fs.readFileSync(dest, 'utf8'); // 直接得到正文
  return { path: dest, size: text.length, text };
}
```

要点：

- **校验**：比对文件大小 / 首行标题，失败重下；不要只信“文件存在”。
- **清理**：启动时统计 `books/` 体积，超过 150MB 按“最久未读”淘汰；
  正在读的书加白名单。
- **断点**：中位 27KB，整文件重下即可；只有 >1MB 的大经才值得做 Range 分片
  （`wx.request` + `FileSystemManager.appendFile`）。
- **进度**：`bookId → {fileID, version, size, downloadedAt, lastReadAt}` 存 Storage。
- **更新**：管理员改排版后 `version` 变化，书架显示“可更新”，由用户确认后重下。

### 3.4 阅读器（最花时间的一块）

#### 3.4.1 分段必须与 App 完全一致

笔记是按 `sutraKey + 段落 index` 关联的。只要两端分段规则差一行，历史笔记就会错位。
因此：

- 把 Dart 的 `_parseParagraphs` **一比一移植**成 TypeScript，放进独立模块
  （建议 `utils/parseParagraphs.ts`），包含：
  - 按 `\n` 切行、`trim`、空行跳过；
  - `。。。` 前缀：隐藏该段操作栏；
  - `///` / `／／／`：与下一段不分段；
  - `@@ ... @@`：备注块，整块合并为一段；
  - `BBB` 结尾：加粗段。
- 在笔记数据里增加 `layoutVersion`（或 `contentHash`）：排版更新后若段落数变化，
  走“按段原文重新对齐”的迁移逻辑（App 已有 `_unalignedIndices` 的思路），
  对不上的笔记保留但标记“需重新定位”，不要静默丢弃。

#### 3.4.2 一期：滚动 + 虚拟列表（推荐）

- 用 `scroll-view`（或页面滚动）+ 只渲染可视区上下各 20 段；
  未渲染区域用等高占位，避免 5,000 段一次性 `setData`。
- 每次 `setData` 只更新窗口内数组，**不要**把整本书塞进 `data`。
- 段落点击 → 底部操作条（笔记/复制/朗读可选）；长按 → 段落菜单。
- 进度：`bookId + paragraphIndex + offset`，本地即时写、云端防抖同步。

#### 3.4.3 二期：左右翻页

小程序没有 `TextPainter`，两种做法：

1. **估算**（便宜）：CJK 字宽 ≈ 字号，西文 ≈ 0.55 字号，按段落算行数 → 高度；
   每段高度按 `(书, 字号, 行距, 宽度)` 缓存。误差 1–2%，页面内允许轻微滚动兜底。
2. **实测**（准确但慢）：Canvas 2D `measureText` 逐字测宽、手动折行；
   首次打开一本书时后台分批计算并缓存，显示“排版中”。

```js
// 估算段落高度：够用、零依赖
function lineCount(text, width, fontSize) {
  const perLine = Math.max(1, Math.floor(width / (fontSize + 0.5)));
  let units = 0;
  for (const ch of text) {
    units += /[\u4e00-\u9fff\u3000-\u303f\uff00-\uffef]/.test(ch) ? 1 : 0.55;
  }
  return Math.max(1, Math.ceil(units / perLine));
}
```

#### 3.4.4 选文与画线（最大的交互坑）

- 小程序的 `text` 组件**没有**系统级的“拖拽选择句柄 + 划词菜单”，
  无法像 Flutter 的 `SelectableText` 那样直接拿 `(start, end)`。
- 三条路：
  1. **降级**：只做“整段引用/整段笔记”，不做字符级画线（一期推荐，省 2–3 周）。
  2. **自绘**：长按取触摸点 → 用段落布局缓存反算字符偏移 → 绝对定位高亮层
     + 两个可拖拽手柄；工作量约 8–12 人日，且要处理换行、缩放、深浅色。
  3. **WebView 阅读器**：H5 里 `window.getSelection()` 直接可用，但支付/缓存/分享
     都要走桥接，整体复杂度更高，不建议为了画线引入。

> 如果“笔记”在你们的产品里主要指“写一段感想/备注”，一期完全不用做画线；
> 如果“画线”是核心体验，需要单独排期。

#### 3.4.5 其他

- 字号/行距/背景/夜间：与 App 保持同样的档位，设置存 Storage。
- 目录：多卷经按“卷”拆分（App 已有 `sutraDisplayTitleWithPath` 的卷标逻辑）。
- 搜索：段内 `indexOf`，结果定位到段落；跨书搜索走云端。
- 沉浸阅读：`navigationStyle: custom` + 自定义顶栏，接近 App 的全屏效果。

### 3.5 笔记（复用现有云函数）

现有服务端动作可直接用：

| action | 用途 |
| --- | --- |
| `getParagraphNotes` | 拉某书全部段落笔记（`sutraKey`） |
| `saveParagraphNote` | 保存某段 `notes[]` / `underlines[]` / `done` |
| `deleteParagraphNote` | 删除 |
| `toggleParagraphDone` | 标记“读完/学完” |

数据结构（与 App 一致）：

```json
{
  "sutraKey": "长阿含经T01n0001_001",
  "index": 12,
  "notes": [
    { "id": "n...", "text": "这一段的想法", "quoted": "被引用的原文", "shared": false }
  ],
  "underlines": [{ "start": 3, "end": 18 }],
  "done": false,
  "updatedAt": 1760000000000
}
```

小程序侧补充：

- **离线队列**：本地 `pending_notes` 表，弱网失败后重试；以 `updatedAt` 后写胜。
- **私密优先**：本次范围不含社区，`shared` 一律 `false`；将来若要公开，
  笔记文本必须过 `security.msgSecCheck`（UGC 内容安全）。
- **笔记列表**：按书聚合 + 关键词过滤；全文搜索可先用本地索引，量大再上云端。
- **跨端**：只要 `uid` 打通、分段一致，App 与小程序看到的是同一份笔记。

### 3.6 账号：openid ↔ 现有手机号账号

小程序里拿不到手机号，但有 openid：

1. 小程序调用云函数 → 云函数用 `cloud.getWXContext()` 拿 `OPENID`（需 `wx-server-sdk`）。
2. 新建 `users` 映射：`openid → uid`；首次进入静默建号（`uid = openid` 或独立 uuid）。
3. **与 App 老账号打通**（可选但强烈建议）：
   - 用 `getPhoneNumber`（手机号快速验证，约 0.03 元/次）拿到手机号；
   - 在云函数里按手机号找到 App 原有 `uid`，把 openid 绑过去；
   - 若绑定了微信开放平台，可用 `unionid` 做多端统一。
4. 现有 `api` 云函数的 `resolveUid` 优先信任 `__accessToken`，无 token 时回退
   `TCB_UUID`。小程序调用没有 token，需要补一条“从 `OPENID` 解析 uid”的分支，
   否则笔记会记到另一套 id 下，和 App 数据对不上。

### 3.7 微信支付

#### 3.7.1 资质清单（缺一不可）

| 材料 | 说明 |
| --- | --- |
| 营业执照 | 企业 / 个体工商户；个人不行 |
| 法人身份证 | 正反面 |
| 对公账户 | 个体户可开；用于商户号验证与结算 |
| 小程序认证 | 300 元/年 |
| 微信支付商户号 | 在 pay.weixin.qq.com 申请，选择普通商户 |
| AppID 绑定 | 商户号后台绑定小程序 AppID |
| JSAPI 支付 | 开通后才有 `openid` 支付权限 |
| 结算账户 | 对公；T+1 左右到账 |

#### 3.7.2 支付时序

```
小程序                 pay 云函数                   微信支付 v3
  │  createOrder(bookId)  │                            │
  ├──────────────────────►│  服务端定价、建 pending 订单 │
  │                       ├───────────────────────────►│ JSAPI 下单
  │                       │◄───────────────────────────┤ prepay_id
  │◄──────────────────────┤ 返回 timeStamp/nonce/package/paySign
  │  wx.requestPayment    │                            │
  ├──────────────────────────────────────────────────►│ 用户支付
  │                       │◄───────────────────────────┤ 支付回调 notify
  │                       │ 验签 + 解密 + 幂等更新订单   │
  │                       │ 写 entitlements（发权益）    │
  │  查单/轮询             │                            │
  ├──────────────────────►│                            │
```

#### 3.7.3 云函数骨架

```js
// pay 云函数（独立于 api，隔离商户私钥）
const cloud = require('wx-server-sdk');
const crypto = require('crypto');
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV });

const APPID = process.env.WX_APPID;
const MCHID = process.env.WX_MCHID;
const KEY = process.env.WX_API_V3_KEY;      // 32 字节
const PRIVATE_KEY = process.env.WX_MCH_PRIVATE_KEY; // 商户私钥 PEM

function rsaSign(message) {
  return crypto.createSign('RSA-SHA256').update(message)
    .sign(PRIVATE_KEY, 'base64');
}

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext();   // 小程序调用时自动注入
  if (event.action === 'createOrder') {
    const price = await getPriceFen(event.bookId); // 只信服务端
    const outTradeNo = `HD${Date.now()}${Math.floor(Math.random() * 1000)}`;
    await db.collection('orders').add({
      data: { outTradeNo, uid: OPENID, bookId: event.bookId, price,
              status: 'pending', createdAt: Date.now() },
    });

    const body = JSON.stringify({
      appid: APPID, mchid: MCHID,
      description: '慧灯阅读·书籍',
      out_trade_no: outTradeNo,
      notify_url: 'https://<你的云函数 HTTP 地址>/payNotify',
      amount: { total: price, currency: 'CNY' },
      payer: { openid: OPENID },
    });
    const ts = Math.floor(Date.now() / 1000).toString();
    const nonce = crypto.randomBytes(16).toString('hex');
    const auth = rsaSign(`POST\n/v3/pay/transactions/jsapi\n${ts}\n${nonce}\n${body}\n`);
    // POST https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi
    // Header: Authorization: WECHATPAY2-SHA256-RSA2048 mchid="...",nonce_str="...",
    //         signature="...",timestamp="...",serial_no="..."
    const prepayId = await postWechatPay(body, auth);
    const pkg = `prepay_id=${prepayId}`;
    return {
      timeStamp: ts, nonceStr: nonce, package: pkg, signType: 'RSA',
      paySign: rsaSign(`${APPID}\n${ts}\n${nonce}\n${pkg}\n`),
    };
  }
  // queryOrder / refund / ...
};
```

#### 3.7.4 关键实现点

- **金额**：`total` 以“分”为单位，必须服务端从价格表算，绝不接受客户端传价。
- **订单号**：`out_trade_no` 全局唯一，建议带业务前缀 + 时间 + 随机。
- **回调验签**：用微信支付平台证书/公钥验 `Wechatpay-Signature`；
  解密 `resource` 用 APIv3 密钥（AES-256-GCM，`ciphertext` base64）。
- **幂等**：回调可能重复。用 `update where({ outTradeNo, status: 'pending' })`
  做条件更新，只有第一次生效；发权益也要幂等。
- **查单兜底**：前端支付成功后轮询 3–5 次 `queryOrder`，不能只依赖回调。
- **退款 / 关单 / 对账**：都要做后台页面；对账下载微信账单，按日核对。
- **云开发简化方案**：如果后台仍支持 `cloud.cloudPay.unifiedOrder`，
  可省掉证书与回调域名，但要确认当前云开发环境是否仍开放该能力；不支持就走上文 v3。

#### 3.7.5 收费对象怎么设计（很关键）

| 模式 | iOS | 资质压力 | 建议 |
| --- | --- | --- | --- |
| 卖单本电子书 | 不可卖 | 出版物资质 + 版权 | 谨慎；公版书卖内容容易引发“凭什么收费”的投诉 |
| 会员（离线/同步/排版等增值） | 不可卖 | 相对低 | **推荐**：卖“服务”而不是“公版经文本身” |
| 随喜/资助 | 不可卖 | 慈善法 + 微信规范 | **不建议**搬小程序；现有个人收款码已属灰区 |
| 实体书/周边 | 可卖 | 电商资质 | 与本次范围不符，但可作为 iOS 的合规变现补充 |

### 一期（MVP，建议 4 周内）

## 7. 建议的落地顺序

**Phase 0（并行，1–2 周）**
1. 确认主体：企业/个体户？宗教许可证？出版物许可证？
2. 注册/认证小程序，完成备案；
3. 用“免费阅读”类目去提审一个 3 页 Demo（书城 + 阅读 + 笔记），**先验证能不能过**。

**Phase 1（3–4 周）**
4. 正文迁云存储，书目入云数据库；
5. 阅读器（滚动 + 虚拟列表）+ 段落笔记；
6. 微信登录 + 手机号绑定，打通 App 笔记。

**Phase 2（2 周）**
7. 支付/订单/权益（仅 Android），iOS 隐藏购买；
8. 退款、对账、客服补单。

**Phase 3**
9. 翻页、画线、批量下载；
10. 视资质申请 iOS 虚拟支付。

> 不要先做支付。审核规则不明时，支付代码写得再好也可能整包被拒；
> 先用免费版把“类目 + 宗教内容”这道门探明，是成本最低的顺序。

## 8. 需要你确认的 5 件事

1. **主体**：现在有企业/个体户营业执照吗？有《互联网宗教信息服务许可证》吗？
2. **收费对象**：卖单本、卖会员，还是继续“资助”？三者合规路径完全不同。
3. **iOS**：能接受 iOS 端只能看免费书/已购内容吗？
4. **笔记**：必须和 App 现有笔记互通吗？画线是刚需还是可二期？
5. **“下载”**：能接受“仅小程序内离线缓存、不能导出文件”吗？

这 5 个问题定下来，才能给出准确的排期与报价；否则只能给区间。
