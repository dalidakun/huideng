# 燃灯 App 接入支付宝（App 内支付）方案

> 适用版本：3.4.1+33 · 包名 `com.huideng.reader` · 后端腾讯云 CloudBase（`api` 云函数）
> 状态：方案稿 + 参考实现（`docs/alipay/`），尚未联调。落地前先看 §1 的资质门槛。

---

## 0. 一句话结论

**技术上不难，难在资质。** 支付宝「APP 支付」是签约类产品，签约主体必须是**企业或个体工商户**，个人支付宝账号签不了。拿到资质后，链路是：

```
App 点「资助」→ 云函数下单（服务端定价 + RSA2 签名）→ 客户端调起支付宝 SDK
→ 用户付款 → 支付宝异步通知云函数（验签 + 幂等置为已支付）→ 客户端主动查单兜底 → 感谢页
```

当前 `lib/donate_page.dart` 是「贴收款码让用户自己扫码」的方案，属于远程非面对面收款，按央行 259 号文处于灰区，且无法自动确认到账。换成商户支付反而是更合规的方向。

## 1. 先决条件（90% 的失败都在这一步）

### 1.1 主体资质

| 项 | 要求 |
| --- | --- |
| 支付宝开放平台账号 | 完成**企业 / 个体工商户实名认证**（营业执照、法人身份证、对公账户打款或法人扫脸） |
| 个人账号 | 可以创建应用、调部分开放能力，**不能签约 APP 支付**（签约页会要求营业执照） |
| 结算账户 | 对公账户（个体户也可开）；到账后自行申报纳税 |
| 应用信息 | 应用名称、Android 包名 `com.huideng.reader`、**发布签名 MD5**、应用截图、APK 下载地址（你们官网 `site/download.html` 可用） |

没有营业执照时的最短路径：注册**个体工商户**（线上办理，1–3 个工作日，自行办理基本免费，代办几百元）→ 开对公账户 → 再走下面的流程。

### 1.1.1 已经用个人账号登录了，怎么换成个体工商户？

**先理解一件事**：支付宝账号的「主体类型」在实名认证时就定死了，个人实名账号**不能直接改成**个体工商户；开放平台「绑定商家账号」的列表只显示与当前登录账号同主体的账号，所以个人账号下永远只有「个人」可选。

按顺序试两条路：

**路线 A：账号内是否有「升级/变更为企业商家」入口**

- 支付宝 App → 我的 → 商家服务 → 设置/账户信息里找「升级为企业商家」「主体升级」；
- 或 b.alipay.com（商家中心）登录 → 账户中心 → 主体信息 → 升级；
- 有入口就按提示提交营业执照，主体类型选「个体工商户」；没有这个入口，走路线 B。

**路线 B：用营业执照新注册一个企业支付宝账号（绝大多数情况）**

1. 先办个体工商户营业执照，经营者写本人。名称可用「XX市XX区燃灯技术服务工作室」，经营范围建议包含：技术服务、技术开发、技术咨询、软件开发、信息技术咨询、互联网销售（除许可商品）。不要写「宗教」「出版」「捐赠」类目。
2. 准备一个**没注册过支付宝**的手机号或邮箱（一个手机号只能绑一个支付宝账号）。
3. 用执照注册/认证企业支付宝，主体类型选「个体工商户」，完成经营者扫脸 + 对公账户打款验证。
4. 认证通过后登录 open.alipay.com，确认开发者身份已是企业，再创建应用。
5. 应用里「绑定商家账号」——这时列表里才会出现个体工商户主体；随后签约 APP 支付。
6. 原来的个人账号留着日常使用即可；个人账号下已建的应用可以弃用，在企业账号下重建，**包名与签名保持一致**即可。

**材料清单**

| 材料 | 说明 |
| --- | --- |
| 个体工商户营业执照 | 经营者本人，经营范围含技术服务类 |
| 经营者身份证 | 正反面，需扫脸 |
| 对公银行账户 | 个体户可开；部分地区/银行支持线上开户。个别入口允许经营者银行卡，以页面为准 |
| 未注册过支付宝的手机号/邮箱 | 企业账号注册用 |
| 经营场所证明 | 门店照片/租赁合同/网络经营场所，视类目要求 |
| 应用材料 | 名称、包名、发布签名 MD5、截图、下载地址 |

**注意**

- **不要借、买别人的执照**：主体、结算、税务、法律责任全对不上，支付宝会核验经营者本人。
- 企业认证通常要**对公账户打款验证**（随机金额），提前把户开好能省一周。
- 时间预期：执照 1–3 个工作日 → 企业认证 1–2 个工作日 → 开放平台签约 1–3 个工作日。

### 1.2 应用与签约

1. 开放平台 → 创建应用（类型：移动应用）。
2. 添加能力 → **APP 支付**。
3. 设置接口加签方式 → **公钥模式 / RSA2**：上传「应用公钥」，保存平台给的「支付宝公钥」。
4. 填写应用信息：包名、签名、截图、下载地址（审核会真的去下载）。
5. 签约 APP 支付：选经营类目、确认费率与结算方式。
6. 审核通过后拿到：`APPID`、`PID`（2088 开头）、应用私钥、支付宝公钥。

> 类目与页面文案要一致。一个「佛教经藏阅读 + 资助」的 App，审核时可能被要求补充宗教类相关资质（见 §1.3），类目不要乱选。

### 1.3 「资助」场景的合规边界（重要）

- **不要写成募捐。** 《慈善法》规定公开募捐必须由具有公开募捐资格的慈善组织进行，个人不得公开募捐。页面用「资助 / 赞助开发者」表述，说明款项用于服务器、域名、开发维护，**不承诺任何回报**（会员、结缘品、优先功能都算回报，会被认定为经营行为）。
- **不要用「功德箱 / 捐款 / 众筹 / 随喜功德」这类词**做支付页标题；「随喜」可以做口语，但订单标题建议用「燃灯资助」。
- **个人静态收款码不得用于远程非面对面收款**（银发〔2021〕259 号）。现在的贴码页建议尽快替换或下线。
- 若要做「公益捐赠 + 捐赠票据」，只能与有公开募捐资格的慈善组织 / 寺院基金会合作，走对方对公账户与捐赠协议，你方只做入口。
- 宗教内容合规：以宗教信息发布为主的应用，按《互联网宗教信息服务管理办法》可能需要《互联网宗教信息服务许可证》。支付审核、应用商店审核都可能核验，以主管部门要求为准。
- 资助原则上不退款，但支付通道侧仍可退；页面要写清楚，并保留人工退款入口。

### 1.4 费用与周期（以签约页为准）

| 项 | 量级 |
| --- | --- |
| APP 支付费率 | 约 0.6%（部分行业有优惠） |
| 结算 | T+1 到对公账户 |
| 资质办理 | 个体户 1–3 个工作日；对公账户 1–2 周 |
| 开放平台认证 + 签约 | 3–10 个工作日 |
| 开发联调 | 2–4 人日（含 UI） |
| 联调成本 | 真机 0.01 元小额支付 + 退款 |

## 2. 为什么不能「网页跳转 / 贴码」凑合

| 做法 | 能自动确认到账 | 体验 | 风险 |
| --- | --- | --- | --- |
| 贴个人收款码（现状） | 否 | 要跳出 App 扫码或保存图片 | 259 号文灰区；无法对账；金额靠用户手输 |
| `alipays://` 拉起转账页 | 否 | 半自动 | 金额/备注不可靠，可能被风控，无法确认到账 |
| 免签 / 第四方聚合支付 | 有回调 | 自动 | 资金经第三方、费率 2–6%、跑路与合规风险，违反支付宝协议，可能被封号 |
| **官方 APP 支付** | **是** | 原生收银台 | 需企业/个体户资质 |

结论：要「程序内部付款」且能自动确认，只有官方 APP 支付这一条正路。

## 3. 技术方案

### 3.1 链路

```
App(Flutter)                 云函数 api                      支付宝
    │  createPayOrder            │                              │
    ├───────────────────────────>│ 服务端定价 → out_trade_no     │
    │                            │ 写 payOrders(pending)        │
    │                            │ RSA2 签名 → orderStr         │
    │<──────── orderStr ─────────┤                              │
    │ 原生 SDK 调起收银台          │                              │
    ├────────────────────────────┼─────────────────────────────>│ 用户付款
    │                            │<── notify（异步，验签）───────┤
    │                            │ 幂等置 paid                   │
    │  queryPayOrder（轮询兜底）    │                              │
    ├───────────────────────────>│ alipay.trade.query 主动查      │
    │<──────── paid ─────────────┤                              │
```

### 3.2 四条铁律

1. **私钥只在服务端**：放云函数环境变量，绝不进 APK（反编译即可拿到）。
2. **金额由服务端决定**：客户端只传档位或金额，服务端校验范围并自己拼 `total_amount`。
3. **客户端结果不算数**：SDK 返回 `9000` 只用于切 UI，真正的「已支付」以异步通知或主动查询为准。
4. **通知必须验签 + 幂等 + 校验金额**：否则可伪造通知白拿「已支付」状态。

### 3.3 数据模型 `payOrders`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `outTradeNo` | string | 商户订单号，唯一（建议建唯一索引） |
| `uid` | string | 下单用户（绑定身份，便于查单/客服） |
| `amountFen` | int | 金额（分），**唯一可信金额** |
| `amount` | string | `"6.00"`，与支付宝 `total_amount` 对齐 |
| `subject` | string | 订单标题，如「燃灯资助」 |
| `status` | string | `pending` / `paid` / `closed` / `refunded` |
| `tradeNo` | string | 支付宝交易号 |
| `source` | string | `notify` / `query`（哪条链路确认的） |
| `createdAt` / `paidAt` / `updatedAt` | number | 毫秒时间戳 |
| `client` | string | `android` / `ios`（可选） |

集合权限设为**仅管理端可读写**（客户端不直接读库，只走云函数）。建议索引：`outTradeNo`（唯一）、`uid + status + paidAt`。

## 4. 接入步骤

### 4.1 开放平台配置清单

- [ ] 企业/个体户实名认证通过
- [ ] 创建移动应用，拿到 APPID
- [ ] 上传应用公钥（RSA2 / 2048），保存支付宝公钥
- [ ] 填包名 `com.huideng.reader` + 发布签名 MD5
- [ ] 上传应用截图、下载地址
- [ ] 申请并签约「APP 支付」
- [ ] 记录 APPID、PID、应用私钥（PKCS8）、支付宝公钥
- [ ] （可选）沙箱应用与沙箱买家账号

**取发布签名 MD5**（务必用 release 签名，不是 debug）：

```bash
keytool -list -v -keystore android/app/upload-keystore.jks -alias <alias>
# 取 MD5 指纹，去掉冒号，转小写 32 位
```

也可以直接用开放平台的「应用签名工具」APK 生成。

**密钥格式**：密钥工具导出时选 **PKCS8**（`-----BEGIN PRIVATE KEY-----`）。若只有 PKCS1，先做格式转换，或在环境变量里保留 `RSA PRIVATE KEY` 头。

### 4.2 服务端（云函数）

参考实现：`docs/alipay/pay.js`（零第三方依赖，只用 Node 内置 `crypto` / `https`，和 `trade.js` 风格一致，云函数不需要 `npm install`）。

**环境变量**（云函数控制台 → 函数配置 → 环境变量）：

| 变量 | 示例 | 说明 |
| --- | --- | --- |
| `ALIPAY_APP_ID` | `2021004xxxxxxxxx` | 开放平台 APPID |
| `ALIPAY_PRIVATE_KEY` | `MIIEv...` | 应用私钥（PKCS8，可带/不带 PEM 头，换行可写 `\n`） |
| `ALIPAY_PUBLIC_KEY` | `MIIBIj...` | **支付宝公钥**（不是应用公钥） |
| `ALIPAY_NOTIFY_URL` | `https://xxx.service.tcloudbase.com/alipay/notify` | 必须是公网 HTTPS、443、不能带参数 |
| `ALIPAY_SELLER_ID` | `2088xxxxxxxxxxxx` | 可选，填了会校验通知里的 `seller_id` |
| `ALIPAY_GATEWAY` | 默认正式网关 | 沙箱填 `https://openapi-sandbox.dl.alipaydev.com/gateway.do` |
| `TZ` | `Asia/Shanghai` | **建议设置**：云函数默认 UTC，时间戳会差 8 小时 |

**三处接线**（`cloudfunctions/api/index.js`）：

```js
const pay = require("./pay");

// 1) app 初始化之后（约第 110 行）
pay.init(app);

// 2) HTTP 分支里，postPage 之后（约第 535 行）
const notify = await pay.handleNotify(event);
if (notify) return notify;

// 3) switch (action) 之前（约第 1233 行），放在 trade 处理之后
const payResult = await pay.handle(action, event, uid);
if (payResult !== undefined) return payResult;
```

`pay.js` 提供三个 action：`createPayOrder`、`queryPayOrder`、`listMyPayOrders`，以及 HTTP 通知入口。

**开通通知地址**：云开发控制台 → 云函数 → `api` → HTTP 访问服务，添加路径 `/alipay/notify` 指向 `api`，把生成的域名填进 `ALIPAY_NOTIFY_URL`。通知必须返回纯文本 `success`（`pay.js` 已处理），否则支付宝会重试。

**时间戳坑**：支付宝要求 `timestamp` 为北京时间。`pay.js` 自己按 UTC+8 生成，不依赖服务器时区；`TZ` 仍然建议设置，避免日志与其他 SDK 行为错位。

### 4.3 客户端（Flutter）

`alipay_kit` 等现成插件已多年未维护（最新 6.0.0 发布于 3 年前），你们的 AGP 8.11 / Kotlin 2.2 大概率编译不过。建议自己写一个很薄的 MethodChannel，直接包官方 AAR，约 60 行：

1. `android/app/build.gradle.kts`：

```kotlin
dependencies {
    coreLibraryDesugaring("com.android.tools:desugar_jdk_libs:2.1.4")
    implementation("androidx.core:core:1.12.0")
    // 支付宝 App 支付 SDK（Maven Central，最新 15.8.42）
    implementation("com.alipay.sdk:alipaysdk-android:15.8.42")
}
```

2. `AndroidManifest.xml` 的 `<queries>` 里加包可见性（Android 11+）：

```xml
<queries>
    <!-- 原有条目保留 -->
    <package android:name="com.eg.android.AlipayGphone" />
    <intent>
        <action android:name="android.intent.action.VIEW" />
        <data android:scheme="alipays" />
    </intent>
</queries>
```

3. `MainActivity.configureFlutterEngine()` 里注册通道（文件见 `docs/alipay/AlipayChannel.kt`）：

```kotlin
registerAlipayChannel(this, flutterEngine.dartExecutor.binaryMessenger)
```

4. `proguard-rules.pro`（你们开了 `isMinifyEnabled = true`，不 keep 会崩）：

```proguard
-keep class com.alipay.** { *; }
-keep class com.ta.utdid2.** { *; }
-keep class com.ut.device.** { *; }
-dontwarn com.alipay.**
-dontwarn com.ta.**
-dontwarn com.ut.**
```

5. Dart 侧：`docs/alipay/alipay_service.dart` 提供 `AlipayService.instance.donate(amountFen: 1800)`，内部完成「下单 → 调起 → 查单确认」，返回 `paid / pending / closed / failed`。

### 4.4 资助页交互

把 `lib/donate_page.dart` 下半部分的收款码区域换成：

```
[ 6 ] [ 18 ] [ 36 ] [ 66 ] [ 108 ] [ 自定义 ]
              [ 支付宝支付 ]
```

状态机：

- 未登录 → 先 `LoginPage`，不产生订单（订单必须绑定 uid）。
- 点击支付 → 按钮转 loading，禁止重复点击；服务端有 5 秒防抖，重复会返回 `too_frequent`。
- SDK 返回 `9000` → 文案「支付成功，正在确认…」，轮询 `queryPayOrder`（0.8s / 1.6s / 3.2s）。
- 服务端确认 `paid` → 感谢页（金额、订单号、时间）；不要只信客户端结果。
- `6001` 取消 → 提示「已取消」，订单仍 pending，可重新支付（新单）。
- `8000 / 6004` 结果未知 → 提示「支付结果确认中，可在资助记录查看」，后台继续查。
- 失败 → 显示原因 + 重试；订单号写日志，方便客服。

可选：加一个「资助记录」页，调 `listMyPayOrders`，展示已支付订单（也方便用户自查）。

## 5. 联调与验收

### 5.1 沙箱

开放平台 → 开发工具 → 沙箱：拿到沙箱 APPID、沙箱买家账号、沙箱网关。把 `ALIPAY_APP_ID` 换成沙箱 APPID、`ALIPAY_GATEWAY` 换成沙箱网关，客户端安装支付宝后用沙箱买家账号登录。

沙箱对 APP 支付的支持以沙箱页说明为准；**最终一定要用正式环境 0.01 元真机走一遍**（再退款）。

### 5.2 验收清单

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 未登录点支付 | 引导登录，不建单 |
| 2 | `amountFen` = 0 / 50 / 999999 | 服务端 `invalid_amount` |
| 3 | 正常 0.01 元 | 客户端 9000，3 秒内订单变 paid |
| 4 | 支付中途取消 | 6001，订单仍 pending，可重新下单 |
| 5 | 支付成功后立刻杀进程 | 重启后主动查单能补成 paid |
| 6 | 重放同一条 notify | 状态不变，不重复发货/记账 |
| 7 | 篡改 notify 金额或签名 | 验签失败，返回 failure |
| 8 | 未安装支付宝 | 明确提示 + 引导安装 |
| 9 | 支付中断网 | 提示「结果确认中」，可查单恢复 |
| 10 | 商户平台退款 | 订单标 `refunded`（需另接退款接口或人工） |
| 11 | 并发两次下单 | 第二次被防抖拦下 |
| 12 | release 包（混淆 + 正式签名） | 支付正常，验签通过 |

### 5.3 上线前

- 用 release 签名打包，包名/签名与开放平台完全一致（debug 包会报签名错误）。
- 关掉测试金额下限，确认金额范围（建议 1–2000 元）。
- 云函数日志脱敏：不打印私钥、完整 `orderStr`、`sign`。
- 给 `notify` 异常加告警（验签失败、未知订单、金额不一致）。

## 6. 运维

- **对账**：商户平台（b.alipay.com）下载日账单，与 `payOrders` 的 `paid` 记录比对金额与笔数；差异人工核查。
- **退款**：小额用商户平台手动退；量大了再接 `alipay.trade.refund`（同一套签名）。
- **客服**：订单号（`outTradeNo`）+ 支付宝交易号（`tradeNo`）是排查凭据。
- **税务**：经营所得需申报，保留流水与发票。
- **费率/结算**：以签约页为准；退款通常不退手续费。

## 7. 如果拿不到营业执照：备选方案

| 方案 | 资质 | 到账自动确认 | 建议 |
| --- | --- | --- | --- |
| 维持收款码（现状） | 无 | 否 | 合规灰区，只适合过渡；建议加「转账后留言」人工核对 |
| 爱发电 / 面包多等创作者平台 | 个人 | 平台回调 | 合规、有抽成，但会跳出 App |
| 第三方聚合（虎皮椒、PayJS、易支付） | 个人可接 | 有 | **不建议**：资金过第三方、合规与跑路风险，违反支付宝协议 |
| 免签支付 / 监听通知栏 | 无 | 假回调 | **不要碰**：明确违规，可能涉刑 |
| 注册个体户 + 官方 APP 支付 | 个体户 | 是 | **推荐**，一次性投入换长期合规 |

## 8. 常见坑

1. 私钥打进客户端 —— 最常见也最致命。
2. 把客户端 `9000` 当支付成功 —— 通知丢了就永远对不上账。
3. notify 不验签、不校验 `app_id` / `total_amount` —— 可伪造。
4. notify 重复投递导致重复记账 —— 必须幂等。
5. 金额用 `double` —— 一律用「分」的整数。
6. `total_amount` 与订单金额不一致 —— 必须字符串两位小数比对。
7. release / debug 签名不同 —— 开放平台填的必须是发布签名。
8. 开了混淆没 keep 支付宝 SDK —— 线上崩溃，测试包正常。
9. Android 11 没加 `<queries>` —— 检测不到支付宝，H5 兜底异常。
10. `notify_url` 带参数、非 443、需要登录 —— 收不到通知。
11. 沙箱 APPID 与正式 APPID 混用 —— 签名/应用不匹配。
12. 订单号重复 —— 支付宝直接报错；用时间戳 + 随机数。
13. 云函数时区 UTC —— 时间戳差 8 小时（`pay.js` 已内置 +8，仍建议设 `TZ`）。
14. 支付返回时 Activity 被回收 —— 结果丢失，靠主动查单恢复。
15. 页面写「捐款 / 募捐 / 功德箱」—— 合规风险，改「资助」。

## 10. 建议实施顺序

1. 办个体户/企业资质，开对公账户。
2. 开放平台建应用、配密钥、填包名签名、签约 APP 支付。
3. 部署 `pay.js` + 配环境变量 + 开通 `/alipay/notify`。
4. 加 AAR、Manifest、ProGuard、MethodChannel，先用写死的 `orderStr` 打通收银台。
5. 改资助页 UI，接完整下单/查单流程。
6. 正式环境 0.01 元真机验收，对照 §5.2 清单逐条过。
7. 灰度：先对少量用户开放，观察通知成功率与订单差异。
